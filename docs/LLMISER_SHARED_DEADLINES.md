Later documentation-only commits do not change this verified source snapshot. This follows the [Excel/assembly release](LLMISER_EXCEL_ASSEMBLY_MEMORY.md).

## Scope and behavior

Conversion, start, advance and cron tick routes establish one 300-second invocation deadline at entry. Admission, upload/body parsing and queue setup consume that same time. This is **not a new whole-job lifetime limit**: durable PDF/OCR/archive children and later ticks receive their next invocation's budget. Existing leases, attempt limits, admission, retention, SQL and pool capacity are unchanged.

The dispatcher keeps the existing per-attempt caps (120 seconds normal/archive, 150 seconds OCR), but peer retries share the outer remaining time. It stops backend work 60 seconds before the route deadline to leave time for database outcome recording and result signing. A new attempt requires at least 13 seconds. Backend headers expire two seconds before the transport timer, leaving a response margin. Response-body reading/decoding also consumes the attempt budget. Actual transport timeout or an explicit backend deadline response does not launch the peer during that pass. Legacy transient responses still permit the existing bounded failover when enough time remains.

Internal protocol: optional `X-LLMiser-Deadline-Ms`, an absolute Unix millisecond timestamp. Absolute time accounts for network transfer, Render wake-up and backend thread admission. Only authenticated internal calls validate it: wrong/missing credentials retain the existing authentication errors. Malformed/duplicate deadline fields return 400; expired authenticated calls return 504 with `X-LLMiser-Deadline-Exceeded: 1`. Missing deadline fields preserve legacy limits. A far-future value is capped at 300 seconds on receipt. Browser-provided deadline headers are not forwarded by the frontend.

Workers convert the remaining wall-clock time to a monotonic request-local budget at ASGI entry. Context propagates to FastAPI's sync worker; existing `ThreadPoolExecutor` operations explicitly bind/reset the budget. N/O/Z keep byte-identical `common/` sources. PDF loops, archive entries, parser boundaries, OCR preparation/recognition, merge reads and final writes check that budget. An expiry is not swallowed as one bad ZIP document or returned as a successful partial result.

Compute checkpoints leave ten seconds for worker finalization. OCR and orientation subprocess timeouts shrink to the available compute time. Storage timeouts also shrink, streamed reads check the total deadline between chunks, and writes check again after acknowledgement. An expired output write cannot report successful completion. Database REST calls on start/advance/tick are bounded by both their existing 30-second cap and the outer deadline. Already claimed work follows the existing retry/failure/lease-recovery rules; a failed outcome write is not fabricated as success.

This is cooperative cancellation. A running native parser, lock wait, network operation or synchronous JSON/Markdown operation cannot be forcibly preempted by these checkpoints. HTTPX's connect/read/write/pool timeouts are inactivity limits, not a hard total-transfer timer; chunk/boundary checks complement them. A response or Storage write may already have reached the server when a timeout is detected. There is no new exactly-once write guarantee, atomic multi-object rollback, concurrency increase or billing claim. Shared provider clocks are assumed accurate; clock skew may cause conservative early failure. Remaining parser isolation, storage attempt fencing and capacity work stay separate.

References: [Node AbortSignal](https://nodejs.org/api/globals.html#static-method-abortsignaltimeoutdelay), [Python 3.12 context variables](https://docs.python.org/3.12/library/contextvars.html), [AnyIO thread context/cancellation](https://anyio.readthedocs.io/en/stable/threads.html), [HTTPX timeout semantics](https://www.python-httpx.org/advanced/timeouts/). Context7 tools were unavailable; official documentation and installed-runtime tests were used.

## Validation and rollout

Local/generated checks currently pass: 270 frontend tests, 160 normal/PDF tests, 104 archive tests and 11 focused OCR/capacity tests. Coverage includes slow primary failover, no-time-before-dispatch, body decoding timeout, old-backend failover, expired database calls, queue claim suppression and durable retry recording; authenticated malformed/expired fields, valid/legacy output equality, clamping, duplicate fields, concurrent context isolation, upload-worker propagation, drip reads, slow upload acknowledgement, PDF/ZIP expiry, OCR subprocess budgets and image cleanup. Existing common-package integrity checks remain intact. The prior workstation-wide OCR readiness-suite limitation remains documented in the Excel report; full Linux OCR CI passed before merge and on merged main.

Local lint, production build and dictionary/SQL/blog consistency passed. Before release, eight generated multipart workbook/ZIP requests with future deadline headers passed on all four document workers, confirming old-worker compatibility. Two actual public Storage conversions (XLSX and workbook ZIP), all four output downloads and exact saved-result recovery also passed as baselines; those two generated jobs follow normal retention.

All seven CI jobs passed on PR #17 and merged main, including 270 frontend tests, full normal/OCR/archive suites, PostgreSQL, edge and extension. All six production Vercel status contexts succeeded. Every N1/N2/Z1/Z2/O1/O2 health response reported exactly `9131a2ac6163f22b630b008b40accb482ed3e0b3` and engine readiness. Mixed-version compatibility was retained during rollout: old workers ignored the added header and new workers accepted legacy callers. No provider setting was changed for this rollout.

No UI/localization/blog/visual, database migration, cron SQL, provider environment, supported-format, file-limit or retention change is included. Operator probes and raw evidence stay ignored under `project-docs/deadline-audit/`.

Post-release generated acceptance on 29 October:

- Thirty direct multipart protocol requests passed across N1/N2/Z1/Z2/O1/O2: each returned 401 for wrong authentication, 504 plus the deadline marker for expired authenticated requests, 400 for malformed deadlines, and 200 with complete output for valid/legacy callers. OCR workers read the generated image text correctly. These requests created no Storage jobs.
- Eight workbook/ZIP requests with future deadlines retained exactly the baseline complete Markdown hashes, character/word counts and engines. MarkItDown remains 0.1.9.
- The public frontend Storage flow passed XLSX and workbook-ZIP conversion, all four output-object downloads and fresh-link recovery, matching the pre-release primary Markdown hashes/counts. Two additional jobs completed image-containing ZIP → OCR → project merge and scanned PDF → OCR → PDF merge, preserving both expected OCR sentences, the ZIP Unicode end marker and exact recovered Markdown. Six real generated Storage jobs in total across pre/post/multi-stage checks follow existing retention; no cleanup was manually invoked.
- Twenty public-page/discovery/health and permanent path/query-preserving redirect checks passed. An uncached wake returned normal/OCR/archive each 2/2 ready; existing legacy API routing was unchanged.

Cold-start/slow-failure boundaries were tested with generated/fake-clock fixtures, not a production stress test or a forced Render sleep. Small-file acceptance is not a maximum-size/concurrency or billing guarantee. Authenticated controller operations, real cleanup execution, hard native-process cancellation and replay-safe Storage fencing remain outside this slice.
